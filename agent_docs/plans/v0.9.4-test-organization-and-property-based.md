# Plan: v0.9.4 Test Organization and Property-Based Strategy

## Status

PLANNED (created 2026-02-25).

## Goal

Run a comprehensive audit and modernization of the ferritex test system to:

1. align test organization with Rust Book guidance for unit/integration separation:
   - https://doc.rust-lang.org/book/ch11-03-test-organization.html
2. introduce property-based testing as a first-class verification tool;
3. keep the resulting approach consistent with real-world large Rust repositories and Rust best practices.

## Why this is a priority

The repository now has a large and fast-growing test surface. Without explicit structure:
- duplication and overlap increase,
- change-locality gets worse,
- agent-driven development wastes context on test navigation.

Property-based testing is expected to provide disproportionate feedback per line of test code:
- one invariant -> thousands of generated cases,
- better edge-case discovery,
- lower manual case-enumeration burden.

## Scope

### 1) Test topology audit (Rust-way)

- Inventory all current tests by layer:
  - unit tests close to implementation modules,
  - crate-level integration tests,
  - workspace integration tests.
- Check for organization drift vs Rust Book model.
- Propose canonical folder/module conventions for ferritex workspace crates.
- Identify duplicated assertions and redundant fixture coverage.

### 2) Quality-of-signal audit

- Classify tests by value:
  - behavior-spec tests,
  - regression tests,
  - snapshot/format tests,
  - brittle implementation-coupled tests.
- Flag flaky/slow patterns and non-deterministic checks.
- Define CI-friendly performance budget for test suites.

### 3) Property-based testing adoption

- Select crate and baseline conventions (`proptest` expected unless a better Rust-native option is justified).
- Define where property tests live (module-level and/or dedicated property suites).
- Start with high-leverage invariants in `ferritex-core`:
  - parse/render round-trip stability where applicable,
  - numbering and delimiter consistency,
  - length/units conversion monotonicity and bounds,
  - TOC/heading/list layout invariants,
  - fallback determinism when layout fields are absent.
- Extend to renderer invariants:
  - no invalid DOCX XML fragments,
  - mandatory structural nodes preserved,
  - deterministic output under stable input.
- Add shrinking and seed reproducibility conventions for failure triage.

### 4) PRD -> TDD -> implementation bridge

- Define requirement-to-test translation template:
  - requirement statement,
  - invariant/property,
  - concrete examples,
  - expected failure modes.
- Encode this template in contribution guidelines for future agent sessions.

### 5) Architecture alignment for agent context economy

- Map test suites to domain boundaries (core semantics, renderer contracts, CLI orchestration).
- Ensure each bounded area can be validated with minimal loaded context.
- Document module contracts that property tests enforce.

## Deliverables

1. Test architecture audit report in `agent_docs/` (new markdown doc).
2. Updated test organization conventions in `agent_docs/coding_conventions.md` and/or `docs/`.
3. Initial property-based test suite merged for core critical invariants.
4. CI policy updates (if needed) for property test runtime limits.
5. Session summary update with measured gains and open gaps.

## Exit Criteria

1. Test organization is documented and consistent across workspace crates.
2. Property-based tests are part of default quality gate for selected critical invariants.
3. Developers/agents can map requirement -> property/invariant -> implementation with low friction.
4. No degradation of deterministic CI behavior.
